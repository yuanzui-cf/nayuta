Java is a piece of SHIT

Published: 2025-12-12  •  193k views  •  Reading Time: 45 mins

“世界上只有两种编程语言：一种是天天被人骂的，另一种是没人用的。” —— Bjarne Stroustrup。然而，Java 属于第三种：它是如此地难用、繁琐、笨重，却因为历史惰性和垄断性的企业市场而无处不在，成为无数程序员不得不面对的噩梦。

引言：被神话的“企业级第一语言”

在二十一世纪初，Sun Microsystems 凭借“一次编写，到处运行”（Write Once, Run Anywhere）的口号将 Java 推向了神坛。在那个跨平台环境极度匮乏、C/C++ 内存泄漏和段错误满天飞的年代，Java 凭借自动内存管理（Garbage Collection）和所谓的虚拟机技术，迅速俘获了企业级应用市场。几十年过去了，Java 演变成了商业帝国和臃肿的象征。随着 Rust、Go、Kotlin 以及现代 TypeScript 等语言的兴起，回看 Java，我们发现它早已不是什么先进生产力的代表，而是充满了过时设计理念、臃肿八股文和繁复工程结构的庞然大物。本篇文章将以极其详尽的技术细节，彻底拆解 Java 为什么已经成为现代软件工程的严重毒瘤和落后代表。

第一章：繁琐与臃肿——用生命写模板代码

Java 最直观的毛病，就是它那惨绝人寰的繁琐语法。在 Java 中，“一切皆对象”被极端教条地贯彻执行，导致了极其严重的表达力低下。程序员在写 Java 的时候，至少有 70% 的生命消耗在毫无意义的“样板代码（Boilerplate Code）”中。

要定义一个简单的用户数据传输对象（DTO），在现代语言（比如 TypeScript、Go、Rust）中只需要短短几行。而在 Java 中，你需要写一个完整的类，带有私有字段，然后是长篇大论的 Getter、Setter，还有构造函数、equals()、hashCode() 以及 toString()。即便后来 Java 引入了 Record 或者是社区使用三方工具 Lombok 插件来用注解生成这些方法，也无法从根本上消除 Java 整个语法底层的繁琐本质。以下是一个简单的对比： 

// 现代 Rust 实现
struct User {
    id: u64,
    name: String,
    email: String,
}

// 现代 TypeScript 实现
interface User {
    id: number;
    name: string;
    email: string;
}

// 传统 Java 实现 (不使用 Lombok)
public class User {
    private Long id;
    private String name;
    private String email;

    public User(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        User user = (User) o;
        return Objects.equals(id, user.id) &&
               Objects.equals(name, user.name) &&
               Objects.equals(email, user.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name, email);
    }

    @Override
    public String toString() {
        return "User{id=" + id + ", name='" + name + "', email='" + email + "'}";
    }
}

这就是 Java 程序员每天都要面对的现实。即使使用 IDE 自动生成，或者用 Lombok 注解，这些繁琐的代码依旧存在于编译产物中。Lombok 作为极其广泛的三方库，甚至需要直接去 hack Java 编译器的 AST（抽象语法树）才能工作，这在任何一个健康的编程语言生态中都是不可想象的——这意味着官方编译器缺乏最基本的反射、元编程或宏系统的设计，逼得社区不得不使用这种“邪术”。

第二章：企业级“过度工程”与反射地狱

由于 Java 语言本身的表达能力极为有限，且不支持头等函数（在 Java 8 引入拙劣的 Lambda 表达式和 Functional Interface 之前），因此为了实现所谓的软件设计原则（如 SOLID），Java 社区发明了全宇宙最复杂的“设计模式”和框架体系。这就导致了臭名昭著的过度工程（Over-Engineering）。

在企业级 Java 框架（尤其是 Spring Boot / Spring Cloud）中，你经常能看到令人啼笑皆非的类名：AbstractSingletonProxyFactoryBean、InternalResourceViewResolver 甚至是 BeanPostProcessorRegistrationDelegate。这些冗长类名的背后，是 Java 缺乏强大的语言特性支持，而不得不采用庞杂的多层抽象来弥补。为了在运行时获得动态性，Java 极度依赖反射（Reflection）和运行时注解处理。这引发了一系列灾难性的后果：

  • 破坏编译期检查：Spring 框架通过大量的 XML 配置或 Java 注解在运行时进行依赖注入（DI）和切面编程（AOP）。这意味着，如果配置或类型注入错误，Java 编译器完全一无所知，错误只会在程序启动或运行时爆发。这让 Java 的强类型检查变成了笑话。
  • 黑盒魔法：Java 应用的启动过程像是一个巨大的黑盒。类加载器在后台狂热地扫描整个 Classpath，读取 jar 包中的每一个字节码，寻找 @Component 和 @Autowired 注解，通过反射强行拼装对象。程序员很难看清自己的代码究竟是如何执行的。
  • 构建配置冗长：Maven 依靠庞大臃肿且难以阅读的 XML 文件（pom.xml），即使是现代的 Gradle，其编译和构建速度也常常慢到令人抓狂。

第三章：JVM 的内存吞噬与冷启动硬伤

Java 是运行在 JVM（Java 虚拟机）上的。JVM 内部结构极其复杂，包含 JIT（即时编译器）、垃圾回收器（GC）、类加载子系统等。虽然经过二十余年的优化，JVM 在长期运行下的吞吐量表现不俗，但在如今以微服务、Serverless、容器化（Docker/K8s）为核心的云原生时代，JVM 表现出了致命的硬伤。

首先是内存开销巨大。一个最基础的 Spring Boot Hello World 应用，在不做任何业务处理的情况下，启动后往往就需要占用 200MB - 300MB 的物理内存。而在 Go 或 Rust 中，同等吞吐量的原生 Web 应用仅需要 10MB - 20MB 左右的内存。这种高内存消耗在海量微服务集群下会被无限放大，直接导致企业的云服务账单翻倍增长。

其次是冷启动（Cold Start）延迟。在 Serverless（如 AWS Lambda / Google Cloud Run）环境中，服务需要根据流量动态伸缩。当流量暴增时，平台需要瞬间启动几百个新容器。而 JVM 应用从启动到完全就绪，由于类加载扫描、JIT 热点代码编译等过程，往往需要 5 到 15 秒甚至更久。在 JIT 编译器把代码编译成机器码之前，应用运行极慢。与之对比，Go/Rust 编译出的原生可执行文件启动时间往往小于 10 毫秒，且起步即是全速运行。尽管 Java 社区尝试通过 GraalVM 原生镜像（Native Image）技术来解决这个问题，但因为 Java 生态中大量第三方库极度依赖反射和动态代理，使得将现有的 Java 应用编译为 GraalVM 原生可执行文件需要配置浩如烟海的反射 JSON 文件，极为难用且易崩，纯属削足适履。

第四章：历史局限性——泛型擦除与十亿美元的噩梦

Java 为了维持所谓对旧版本的向后兼容性（Backward Compatibility），背负了沉重的历史包袱，导致其语言设计中存在大量粗糙、不科学的妥协。

1. 伪泛型与类型擦除（Type Erasure）
Java 在 1.5 版本才引入了泛型（Generics），但这并不是真泛型，而是伪泛型。在编译之后，所有的泛型信息都会被“擦除”为默认的 Object。这意味着在运行时，JVM 根本不知道 List<String> 和 List<Integer> 的区别，它们全都是原始的 ArrayList。这也导致了 Java 泛型中无法执行许多直观的操作，比如你不能 new T()，不能 instanceof List<String>，不得不通过传递 Class<T> 对象等令人感到恶心的权宜手段来工作： 

// 由于类型擦除，你不能直接创建泛型对象
public <T> void doSomething() {
    // T obj = new T(); // 编译错误！
}

// 必须写成这种极其别扭的“反射”方式
public <T> void doSomething(Class<T> clazz) {
    try {
        T obj = clazz.getDeclaredConstructor().newInstance();
    } catch (Exception e) {
        e.printStackTrace();
    }
}

2. 空指针异常（NullPointerException）——十亿美元的灾难
Java 中的一切对象引用都可以为 null。这意味着，只要你没有进行防卫性的 if (obj != null) 判断，随时随地都会在运行时抛出 NullPointerException。这被设计界公认为编程史上的“十亿美元错误”。而在现代语言（如 Rust）中，通过 Option<T> 枚举完全在编译期消除了空指针的存在；即使在 Kotlin 或 TypeScript 中，也提供了内置的空安全检查。Java 8 虽然后补了一个 Optional<T> 类，但它只是一个笨重的内存包装，不仅带来了额外的内存分配开销开销，而且由于你可以对一个 Optional 对象本身赋予 null，或者直接强行调用 .get()，它根本没有在编译器层面保证空安全。

3. 强制 Checked Exception
Java 独创了“受检异常（Checked Exception）”概念，要求开发者必须在方法签名中声明抛出的异常，或者捕获处理。原本这一设计初衷是为了让代码更健壮，但实际开发中，它极大地破坏了代码的组合性。因为当你在写 Lambda 表达式或 Stream 时， Checked Exception 会因为方法签名不符导致编译失败，逼得程序员写出无数毫无意义的垃圾捕获代码： 

// 即使你明确知道不会出错，也必须捕获或者抛出 Checked Exception
list.stream().forEach(item -> {
    try {
        // 一个可能抛出 IOException 的操作
        processItem(item);
    } catch (IOException e) {
        // 只能用 RuntimeException 包裹强行抛出，毫无优雅可言
        throw new RuntimeException(e);
    }
});

第五章：拙劣的并发与臃肿的现代化改造

Java 最初的并发模型是基于原生操作系统线程的。由于操作系统线程非常昂贵，一个 JVM 进程最多只能启动数千个线程，这迫使 Java 社区广泛采用高并发下的线程池（ThreadPool）和复杂的异步回调模型（如 CompletableFuture / Reactive Programming）。响应式编程（Reactive Programming）在 Java 中的实现（如 Spring WebFlux / RxJava）被称为“地狱级排版”，其代码完全失去了可读性和可调试性： 

// 响应式 Java 并发代码，极难阅读和断点调试
public Mono<UserDTO> getUser(String userId) {
    return userService.findUser(userId)
        .flatMap(user -> orderService.getOrders(user.getId())
            .collectList()
            .map(orders -> new UserDTO(user, orders)))
        .onErrorResume(e -> Mono.just(UserDTO.empty()));
}

在 Go 语言中，同等逻辑只需要使用轻量级的协程（Goroutines）以及最符合人类直觉的同步阻塞式写法，便能在数百万并发下轻松自如。虽然 Java 21 带来了 Project Loom（虚拟线程），号称能彻底解决高并发问题，但这已经晚了太多年。而且，由于 Java 整个生态库（比如 JDBC 等庞杂的三方库）的历史包袱过于沉重，大量底层库依旧包含很多 synchronized 关键字的阻塞逻辑（这会导致虚拟线程卡死在原生载体线程上，无法释放），导致虚拟线程在实际项目中推进速度缓慢，这正是历史包袱太重导致步子迈不大的典型体现。

第六章：技术生态与效率横向大比拼

为了让事实更加清晰，我们可以通过一张直观的技术对比表，来看看 Java 与现代主流开发语言之间的真实差距：

特性 Java (JVM) Rust Go TypeScript (Node.js)
Hello World 内存占用 约 200MB - 300MB 小于 5MB 约 8MB - 12MB 约 20MB - 30MB
冷启动速度 秒级 (3s - 15s) 毫秒级 (< 10ms) 毫秒级 (< 15ms) 毫秒级 (< 50ms)
空安全机制 Optional 封装 (运行时) Option<T> (编译期安全) 部分空指针风险 可选链、严格模式 (编译期)
并发模型 系统级线程 / 虚拟线程 无畏并发 (Compile-time) Goroutines + Channels 单线程事件循环 (Event Loop)
二进制体积 庞大的 Jar 包 + JVM 运行时 微小、单文件原生二进制 较小、单文件原生二进制 依赖 node_modules 与运行时
开发生产率 极低 (由于大量模板代码) 中等 (严格但安全) 极高 (简洁优雅) 极高 (极速反馈循环)

无论从运行效率、内存开销，还是现代工程急需的敏捷度、快速构建速度来看，Java 全方位落后于时代。它唯一的护城河，就是历史上几十年堆积起来的“屎山”系统（Legacy Systems），以及大厂中那群只懂 Java、依靠八股文面试维持行业门槛的“企业级架构师”们。

结论：让老兵安息吧

Java 是一代传奇，它在互联网爆发的黄金时代立下了汗马功劳，完成了它的历史使命。然而，时代在变，软件工程面临的挑战也在发生翻天覆地的变化。如今的开发需要极高的冷启动响应、极简的云托管成本、极致的安全性和最高的开发生产效率。Java 本身沉重的历史兼容性负担，决定了它只能通过不停地打补丁来假装自己很现代，这导致它的语法正变得越来越混乱和丑陋。

在这个万物上云、微服务与原生编译大行其道的时代，我们没有理由再去新项目中拥抱笨重的 Java。与其忍受冗余的框架配置、冗长的反射魔法和经常在半夜拉响警报的空指针异常，不如去拥抱更优雅的 Go、更有编译期安全保证的 Rust，或者是生态蓬勃又极速反应的 TypeScript。Java 这辆年久失修、布满灰尘的蒸汽机车，是时候让它缓缓驶入历史博物馆，安享晚年了。
